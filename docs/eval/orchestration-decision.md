# 오케스트레이션 결정 근거: STT → 에이전트 병렬 호출

작성 10/5. 결정은 `docs/PLANNING.md` 2장, 기술 결정 기록은 `docs/DECISIONS.md` D-099·D-101이다.

## 결정

진행자의 STT 최종 문장마다 법률(Compliance)·팩트(Facts)·맥락(Context) 에이전트 3개를 **항상 동시에** 호출한다. 앞에 분기(라우터)를 두지 않는다. "무엇을 언제 띄울지"는 3초 경로 밖의 AI PD가 정한다.

## 질문과 판단 기준

- 질문: 문장마다 셋을 다 부를 것인가, 라우터가 필요한 에이전트만 고르게 할 것인가.
- 1순위 정확도: 필요한 에이전트를 한 번이라도 빠뜨리면 그 문장의 법률 경고나 틀린 정보 메모가 화면에 뜨지 않는다.
- 2순위 속도: 진행자가 말을 끝낸 시점부터 잰다 (STT 포함). 법률 위험·틀린 제품 정보는 3초, 프롬프터·질문 확인은 5초.

## 비교한 후보

| 후보 | 방식 |
|---|---|
| 병렬 (채택) | 셋을 항상 동시에 호출 |
| LLM 라우터 (router3) | Gemini 3.5 Flash Lite가 먼저 고르고, 고른 것만 호출 |
| Gemini 목적 라우터 | 같은 모델, 목적별 판단 기준과 프롬프터 포인트를 준 새 프롬프트 |
| Jev | TypeSafe Jev(OpenRouter)가 에이전트별 확률을 주고 임계값으로 호출 |
| 정규식 (팩트만) | 숫자·단위·가격 단어가 있으면 팩트 에이전트 호출 |

## 측정 1: 라우터가 필요한 호출을 놓치는가 (10/4~10/5)

79문장 × 5회 = 395회. 기존 평가 39문장 + 새 스트레스 문장 40개(돌려 말한 위반, 숫자 없는 팩트, 복합 의도, STT 조각, 잡담). 출처 `docs/eval/routing-accuracy.md`.

| 라우터 | 지연 p50 / p95 | 필요한 호출을 놓친 횟수 | 비고 |
|---|---|---|---|
| Jev (임계값 0.3) | 205 / 275ms | 0 | 임계값은 같은 데이터로 고른 값이라 유리하게 나온다. 임계값 0.5에서는 13회 놓침 |
| Gemini 목적 라우터 | 986 / 1,213ms | 23 (팩트 5, 맥락 18) | 예/아니오만 주어서 애매한 문장을 "아니오"로 떨어뜨림 |
| 정규식 (팩트만) | 0.03ms 미만 | 0 | 이 세트의 철자형 숫자 단어를 넣은 결과다. 운영 경로에는 넣지 않음 |

LLM 라우터 router3 (10/2, 39문장 × 20회 = 780회, `docs/eval/agents-compare.md`, `agents-router3.md`)는 필요한 호출을 놓치지 않았다. 다만 라우터 자체가 p50 985ms, p95 1,161ms였다.

## 측정 2: 라우터가 속도를 얼마나 늦추는가

컴플라이언스 판정이 나오기까지의 시간이다 (STT 최종 문장 도착부터).

| 구조 | 측정 | p50 | p95 |
|---|---|---|---|
| 병렬 3개 | 10/2, 39 × 20회 | 1,196ms | 1,510ms |
| 병렬 3개 (운영 에이전트) | 10/3, 39 × 20회 (`agents-split3-prod.md`) | 1,143ms | 1,390ms |
| LLM 라우터 + 선택 호출 | 10/2, 39 × 20회 | 1,990ms | 2,384ms |
| 병렬 3개, 처음 보는 문장 | 10/5, 100 × 3회 (`holdout-split3.md`) | 1,046ms | 1,270ms |

LLM 라우터는 정확도를 올리지 못하고 0.5~0.9초를 더했다. Jev는 0.2~0.3초를 더한다.

## 측정 3: 병렬 구조의 정확도, 처음 보는 문장 (10/5)

100문장 × 3회 = 300회, 캐싱 끔. 라벨 두 개(H078, H049)를 검토자 A의 독립 판정으로 고친 뒤 저장된 답변으로 다시 채점했다 (모델 재호출 없음). 출처 `docs/eval/holdout-split3-relabeled.md`, 원래 채점은 `holdout-split3.md`.

| 항목 | 결과 |
|---|---|
| 위반 발언 잡기 (맞는 규정) | 75/75 (100%) |
| 정정 인식 | 18/18 (100%) |
| 질문 답변 연결 | 69/69 (100%) |
| 프롬프터 포인트 | 57/57 (100%) |
| 제품 전환 | 24/24 (100%) |
| 틀린 정보 잡기 (모델 출력) | 42/42 (100%) |
| 틀린 정보 잡기 (인용 검사 후) | 39/42 (92.9%). 놓친 3건은 모두 세트 타임세일가(H046)이고, 인용 검사가 맞는 답을 지운 버그다 (수정 중) |

라벨 판정: 검토자 A가 제품 문서·규정·프롬프트만 근거로 13건을 독립 판정했다. 모델이 맞고 라벨이 틀린 것 2건, 라벨이 맞고 모델이 틀린 것 2건(H076, U29), 검증기 버그 1건(H046), 애매 3건, 라벨 맞음 5건.

## 3초 예산 계산

- STT: 말 끝에서 최종 문장까지 p50 0.88초, p95 1.04~1.69초 (`docs/eval/latency.md`)
- 병렬 컴플라이언스 판정: p95 1.27~1.39초
- 합: 약 2.3~3.1초. 각 단계의 p95를 더한 값이라 실제 전체 p95보다 보수적이다.
- 라우터를 앞에 두면 여기에 Jev 0.28초, LLM 라우터 1.16초(p95)가 더해져 3초를 넘는다.

## 그 밖의 확인

- **문장마다 검색 제외.** Vertex AI Search 청크 검색은 p95 2.2초, 158회 중 66회 결과 없음 (10/5). 제품 문서는 작아서(제품당 약 1,350토큰) 통째로 넣는다.
- **ADK 오버헤드.** 가짜 에이전트 3개로 쟀을 때 ADK `ParallelAgent`가 더하는 시간은 1~10ms다 (10/4, 각 40회). 병렬 호출을 ADK 구조로 감싸도 속도 손해는 거의 없다.
- **연속 문장.** 다음 문장은 앞 문장의 판정을 기다리지 않는다 (D-101).

## 대가와 보완

- 병렬은 문장마다 Gemini를 3번 부른다. Jev 기준으로 라우터가 줄일 수 있는 호출은 약 40%다.
- 보완은 명시적 캐싱이다. 처음 보는 문장 100개 × 3회에서 잰 입력 토큰과 캐시 비율은 아래와 같다 (10/5, `holdout-split3.md` 캐싱 끔, `holdout-split3-cache.md` 캐싱 켬).

  | 에이전트 | 입력 토큰 평균 | 캐시 비율 (끔) | 캐시 비율 (켬) |
  |---|---|---|---|
  | 컴플라이언스 | 2,517 | 0% | 0% |
  | 맥락 | 2,371 | 0% | 0% |
  | 팩트 | 4,947 | 44.1% (Gemini 자동 캐시) | 72.5% |

- 컴플라이언스와 맥락은 Gemini 3 캐시 최소 길이(4,096토큰)보다 짧아 캐시되지 않는다. 팩트 체커만 효과가 있다.
- 캐싱을 켜도 정확도와 속도는 측정 오차 안에서 같다 (컴플라이언스 p95 1,270 → 1,242ms, 팩트 p95 1,599 → 1,643ms).
- 문장 하나당 입력은 약 9,800토큰이다. 5초에 한 문장이면 시간당 약 700만 토큰이다 (추정). 실측 비용표로 방송 1시간당 비용을 확인한다.
- 기존 39문장을 새 코드로 다시 잰 결과 (10/5, 39 × 3회, `agents-split3-1005.md`): 컴플라이언스 p95 1,326ms, 시간 초과 0/117. 프롬프트 순서가 바뀌고 팩트 체커가 제품 문서 전체를 받으므로 D-099 기록과 1:1 비교는 아니다.

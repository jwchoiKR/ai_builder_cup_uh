# 기획 기록 (AI Builder Cup 2026)

진행 중인 기획을 날짜순으로 기록한다. 결정이 바뀌면 이 문서를 고친다. 기술 결정의 상세 근거는 `docs/DECISIONS.md`, 측정 원본은 `docs/eval/`에 있다.

마지막 갱신: 10/5

## 1. 서비스 목표

- **방송 중에** 진행자를 돕는 어시스턴트다. 방송 밖 기능(녹화본 검토, 연습 도구, 방송 전 배너 검사)은 만들지 않는다.
- **ROI 확보 (인력 감축).** 진행자 옆에서 사람이 하던 일을 AI가 맡는다.
  - MD: 댓글 응대, 제품 정보 확인
  - PD: 진행 지휘 (시간 관리, 다음에 할 말, 제품 전환 시점, 답할 질문 선택)
  - 심의 담당: 위반 발언 감시
- **운영자를 없애는 것이 아니라 줄인다 (10/5 사용자).** 덱과 영상은 "운영자 없이"가 아니라 "운영자가 하던 일 중 AI가 처리한 비율"(실측 업무량 집계)로 말한다. 민감한 질문 승인처럼 사람이 해야 하는 일은 운영자에게 남긴다. 1인 모드 기능은 유지하되, 데모는 "운영자가 거의 손대지 않아도 되는" 장면으로 잡는다.
- **초보자도 1인 방송을 할 수 있게 한다.** 기준은 "이 도구를 쓰는 동안 초보자가 중급 진행자만큼 진행한다"이다. 초보자를 가르치는 학습 플랫폼이 아니다. 코칭 리포트나 교육 기능은 넣지 않는다.
- 1인 진행자가 늘면 제품을 알리는 사람이 늘고, 라이브 커머스 시장이 커진다.

## 3. 측정 결과 (10/4~10/5, Vertex AI, 프로젝트 `separk-cloocus`)

### 3.1 라우터 비교 (분기 정확도만, 79문장 × 5회 = 395회)

79문장은 기존 평가 39개와 새 스트레스 문장 40개(`data/eval/route_cases.jsonl`)다. 스트레스 문장은 agy가 쓰고 Claude가 라벨 4개를 고쳤다. 원본: `docs/eval/routing-accuracy.md`

| | Jev (`typesafe/jev-1.13`) | Gemini 3.5 Flash Lite |
|---|---|---|
| 지연 p50 / p95 | 205 / 275ms | 986 / 1,213ms |
| 시간 초과 | 0/395 (마감 500ms) | 3/395 (마감 1.5초) |
| 필요한 호출을 놓친 횟수 | 0 (확률 임계값 0.3 이하), 13 (임계값 0.5) | 23 (팩트 5, 맥락 18) |
| 출력 | 에이전트별 확률 | 에이전트별 예/아니오 |

- Jev 임계값 0.3은 같은 데이터로 고른 값이라 실제보다 유리하게 나온다.
- Gemini는 첫 버전 프롬프트이고, 확률 없이 예/아니오만 받았다.
- 기존 LLM 라우터 프롬프트(`router.md`) 행은 마감 설정 오류(500ms)로 395회 모두 시간 초과가 나서 무효다. 10/2 측정(router3)으로 대신한다. 그때 필요한 호출 누락은 0건이었고, 라우터 p50은 985ms였다.
- 가장 정확한 라우터를 써도 "셋 다 호출"보다 정확도가 나아지지 않는다. 줄어드는 것은 호출 비용뿐이다.

### 3.2 현재 구조(split3) 1회 점검 (39문장, 10/4)

- 정확도 점검 항목 전부 100%
- 컴플라이언스 판정 p50 1,243ms, p95 1,661ms (STT 결과 도착부터)
- STT는 말 끝에서 최종 텍스트까지 p50 0.88초, p95 1.04~1.69초 (`docs/eval/latency.md`)

### 3.3 Google ADK 오버헤드 (가짜 에이전트 3개, 모델 호출 없음, 각 40회)

| 방식 | 결과 도착 지연 p50 | p95 |
|---|---|---|
| asyncio | 6~14ms | 12~19ms |
| ADK ParallelAgent | 7~22ms | 17~29ms |

Windows 타이머 해상도(약 15ms)를 빼면 ADK가 더하는 시간은 1~10ms다. ADK 2.11에서 `ParallelAgent`는 사용 중단(deprecation) 경고가 나므로 버전을 고정한다.

### 3.4 Vertex AI Search

- 데이터 스토어 `daon-product-sheets` (global, 레이아웃 파서, 레이아웃 기반 청킹)를 만들고 제품 PDF 2개를 올렸다 (10/5).
- 청크 검색 지연 (평가 문장 79개 × 2회 = 158회, 이 PC에서 global 엔드포인트, 10/5):

  | | p50 | p95 | max |
  |---|---|---|---|
  | 순차 | 2,120ms | 2,197ms | 2,340ms |
  | 동시 4개 | 1,986ms | 2,139ms | 2,356ms |

- 158회 중 66회는 결과가 비었고, 1등 결과가 방송 중인 제품 문서에서 나온 것은 66회였다. 진행자의 구어체 문장은 검색어로 맞지 않는다.
- **결정 (제안, 사용자 확인 대기):** 문장마다 검색하지 않는다. Vertex AI Search는 문서 파싱과 청킹에 쓰고, 방송 시작과 제품 전환 때 그 제품의 청크를 통째로 받아 메모리에 둔다. 팩트 에이전트는 메모리에서 꺼내 쓴다. 문장마다 검색하면 팩트 경로가 STT 1.7초 + 검색 2.2초 + 판정 약 1.5초로 5초를 넘는다.

## 5. 실행 계획 (3라운드 검토 반영, 미결 사항 결정 후 확정)

### 5.1 AI PD 설계 원칙 (3라운드 합의)

- **발화 말고 다른 사건에도 반응한다.** 질문 도착, 타이머, 프로모션 시작·종료, 제품 전환, 6초 이상 침묵.
- **말할 문장을 보여준다.** 내부 코드("cr-p4 미완료") 대신, 바로 읽을 수 있는 한 줄 문장과 관련 시청자 질문을 띄운다. 기존 질문 카드의 추천 답변(`frontend/src/screens/host/Questions.tsx`)을 재사용한다.
- **카드는 한 번에 하나, 고정한다.** 진행자가 처리하거나 넘길 때까지 유지한다. 조건이 사라지면(프로모션 종료, 질문 답변 완료, 제품 전환) 지우고 정해진 규칙의 기본 카드로 돌아간다.
- **우선순위.** 긴급 경고·팩트 메모(AI PD 우회) > 팀 모드의 운영자 지시 > 답하지 않은 시청자 질문 > 빠뜨린 필수 포인트 > 자연스러운 쉼에서 마무리·전환 제안.
- **하지 않는 것.** 반복 카운트다운, 필수 포인트 재촉, 진행자가 답하는 중에 카드 교체, 댓글 양만 보고 내리는 지시.
- **1인 모드 조작.** 방송 시작·종료, 프로모션 켜기, 제품 전환 수락, 카드 넘기기를 진행자 화면에서 한다. 운영자에게 가던 민감 질문과 미검증 답변 초안은 "보류"로 표시하고 안내 문구를 쓴다. 막혀 있던 답변을 자동으로 허용하지 않는다.
- 영상에 쓸 최소 장면: 초보자가 묶인 시청자 질문과 답변 문장을 받아 답한다 → 다음 필수 포인트를 받는다 → 실수한 표현을 즉시 경고로 고친다 → 제품 전환 제안을 수락한다. 운영자 개입은 없다.

### 5.1.1 AI PD 설계안 v1 (10/5)

- **LLM은 무엇을 띄울지만 고른다.** 화면 문장은 검증된 것만 쓴다. 질문 답변은 `verify_answer`를 통과한 추천 답변, 포인트는 프롬프터 포인트 문구, 프로모션은 등록된 진행자용 문구다. LLM이 새 문장을 지어내지 않는다.
- **판단 시점:** 문장 판정 반영 후, 상위 질문 변경, 제품별 계획 시간의 80%·100%, 프로모션 종료 60초 전, 8초 이상 침묵 (STT는 문장이 끝나야 결과를 주므로 6초 대신 8초).
- **카드:** 질문 답하기, 포인트 말하기, 프로모션 안내, 마무리·전환.
- **안정성:** 빨간 경고 중에는 카드를 띄우지 않는다. 15초 동안 바꾸지 않는다. 완료 판정은 맥락 에이전트의 큐 완료 표시(`covered_cue_ids`)를 재사용한다. 진행자는 키 하나로 넘긴다. 실패·시간 초과 시 규칙(남은 필수 포인트 > 상위 질문)으로 고른다.
- **ADK:** AI PD를 ADK `LlmAgent`(Gemini 3.5 Flash Lite, 구조화 출력)로 먼저 만든다. 연속 발화 작업(codex)이 끝나면 세 에이전트를 `ParallelAgent`로 감싸 루트 오케스트레이터 아래에 둔다.
- **역할:** 백엔드 Claude, 진행자 화면 카드 agy.

### 5.1.1.1 AI PD 카드 범위 변경 (10/5, 사용자 지적, codex·agy 동의)

- "SAY THIS POINT"(포인트 말하기) 카드를 뺀다. 프롬프터 칸이 이미 아직 안 말한 첫 필수 포인트를 크게 강조하므로 중복이다 (사용자: 자리만 차지한다).
- 보완: 프롬프터 칸 안에 "필수 포인트 N개 남음 · 남은 시간" 표시, 계획 시간 80% 이후 남은 필수 포인트를 칸 안에서 한 번 강조 (침묵할 때마다 깜빡이지 않음), 전환·마무리 카드에 남은 필수 포인트를 함께 넣음.
- AI PD 카드는 프롬프터에 없는 것만 맡는다: 답할 질문, 타임세일, 전환·마무리, 읽어주기·불러주기. 띄울 게 없으면 카드를 띄우지 않는다.
- 같은 날 화면 변경 (D-106): YOUR PROMPTER를 프로토타입처럼 고정 크기 제품 칸(가격·성분 함량·말할 포인트, 주의, 피할 말)으로 바꾸고, 심의 경고(HIGH·MEDIUM)가 이 칸을 대신 차지한다. 팩트 메모도 같은 칸으로 옮기고, 내용이 길어도 잘리지 않게 고치는 중이다.

### 5.1.2 댓글 처리 속도와 진행 재료 (10/5)

- 댓글 분류: 대기 중인 질문 댓글이 1개면 바로, 여러 개면 최대 2초·10개까지 모아 한 번에 분류한다 (적응형 소배치). 값은 댓글 몰아치기 테스트로 정한다 (사용자: "테스트하면서 보자").
- 문제 (사용자 지적): 질문을 들어오는 대로 다 빨리 처리하면 방송 후반에 진행자가 꺼낼 이야깃거리가 없다. 댓글 읽어주기는 라이브 커머스의 핵심이다 (인터뷰 #9, #11).
- 결정 (사용자 승인, 개발 세션에 전달):
  0. 질문 저장고와 페이싱: 진행자용 질문은 저장고에 두고 AI PD가 쉬는 순간·주제가 끝난 순간에 하나씩 꺼낸다. 질문 카드 최소 간격은 45초(시작값)다. 저장고가 비면 지난 방송에서 자주 나온 질문을 진행 재료로 쓴다. 민감한 질문은 기존 확인 절차를 따른다.
  1. 많이 물어본 질문 읽어주기 (`read_question`): AI가 채팅에서 답한 질문도 묻는 사람이 3명 이상이면 진행자 카드로 준다. 문장은 검증된 답변을 그대로 쓴다.
  2. 구매·인사 댓글 불러주기 (`shout_out`): "방금 샀어요", "처음 왔어요", 칭찬 댓글을 이름과 함께 정해진 틀로 준다. 키워드 규칙으로 고르고 LLM은 부르지 않는다.
  3. 타이밍: 1·2번과 저장고 질문은 늦은 시간의 필수 포인트보다 낮은 우선순위이고, 쉬는 순간이나 주제가 바뀔 때만 나온다.

### 5.1.3 시험 결과 수치의 필수 문구 (10/5, Claude·codex·agy 논의 후 사용자 결정 A)

- 문제: 새 평가(v2)의 잘못된 경고 6건이 모두 시험 결과 수치를 "in our in-house test" 없이 말한 문장이었다. 맞는 규칙이 없어 판정 에이전트가 과장 표현이나 노화·생리 기능(빨간 경고) 규칙을 끌어다 썼다.
- 결정: 시험 결과 **숫자**를 말할 때는 항상 자사 시험임을 밝히게 한다 (정책 확대). 일반 효능 표현은 제외한다. 이유는 제품 문서가 이미 그 수치를 "소규모 자사 시험 결과"로 적고 있고, 숫자는 가장 단정적으로 들리며 (인터뷰 #5), 모델은 이미 이 문장을 잡지만 규칙이 없어 엉뚱하게 분류하기 때문이다.
- 규칙: 전용 규칙 하나를 새로 만든다. **MEDIUM(노란 배너)만, 빨간 경고는 안 된다.** 대신 말할 문장은 승인 문구 목록에서만 가져온다 (제품별 수치·측정 시점·필수 문구 포함).
- 판정: 기존 판정 에이전트가 의미로 판단하고, 코드가 이 규칙의 심각도와 문장을 강제한다. 다른 규칙의 HIGH를 자동으로 내리지는 않는다 (진짜 위반이 묻힐 수 있음, codex 의견 채택).
- 수치까지 틀릴 때: 진행자 카드는 하나로 합친다 (예: "+45% (70% 아님), 'in our in-house test'를 붙여 말하세요"). 기록과 채점에는 두 문제를 따로 남긴다.
- 평가: 해당 라벨(H052·H053·H064·H059·H032)을 고치고, 이 케이스는 회귀 시험으로 돌린다. 처음 보는 새 문장을 따로 만든다.
- 대가: 노란 배너가 늘어난다. 같은 수치는 제품당 한 번만 알리는 식으로 줄인다. 화면에서 확인하며 다듬는다 (사용자).

### 5.1.4 제품별 주장 묶음 자동 추출과 새 제품 등록 (10/5, Claude·codex·agy 논의 후 사용자 결정 B)

- 문제 (사용자 지적): 필수 문구·금지 주장 같은 케이스는 제품마다 달라서, 손으로 넣은 예시로는 새 제품을 다룰 수 없다.
- 결정: 준비 화면(`/setup`)의 Brief Agent를 확장해 제품별 주장 묶음을 만든다. 새 에이전트나 추가 호출은 없다.
  - 뽑는 것: 시험 수치와 조건(인원·자사/임상·측정 시점·원문 인용), 필수 문구와 승인된 대신 말할 문장, 그 제품의 금지 주장, 조건이 필요 없는 일반 효능 표현. 문서에 없는 조건은 "모름"으로 둔다.
  - 운영자가 한 줄씩 확인해야 방송에 쓰인다. AI가 만든 문장이 확인 없이 승인 문구가 되지 않는다.
  - 확정된 묶음은 방송 시작 때 고정해 판정 에이전트 입력에 넣는다. 크기를 제한하고 지연을 잰다.
  - 지난 방송의 넘긴 경고·진행자 정정은 다음 준비 때 제안으로만 보여주고, 사람이 승인해야 반영한다. ASEAN 법정 규정은 바꾸지 않는다.
  - 다른 규칙의 HIGH 경고를 자동으로 내리지 않는다 (5.1.3 유지, agy 재제안 불채택).
- **범위 B (사용자 결정, "작업이 크더라도 완벽한게 중요하다"):** 이미 등록된 두 제품뿐 아니라, 아무 제품 PDF를 올려도 제품 등록과 문서 추출이 되게 만든다. 지금은 업로드가 등록된 제품 코드와 정해진 문서 제목 구조를 요구한다 (codex 확인). 판매자마다 다른 문서 형식은 Vertex AI Search 레이아웃 파서로 읽는다.
- 완료 기준 (제안, codex·agy와 확정 예정): 형식이 다른 처음 보는 제품 문서 3개 이상, 사람이 미리 만든 정답표 대비 시험 수치·조건·금지 주장 누락 없음, 그 제품의 실시간 문장 판정에서 경고 종류·심각도 일치와 빨간 오판 0건, AI가 지어낸 문장의 승인 문구 유입 0건. 시험 문서는 agy, 정답표는 codex가 따로 만든다.

### 5.5 GCP 서비스 검토 (10/5)

- 대회 주제 페이지 기준 필수는 Gemini/Gemma(또는 Agent Platform·Antigravity·AI Studio)와 Cloud Run·Firebase 배포다. 특정 서비스 가산점은 없다. 실제 문제를 푸는 곳에만 쓴다.
- 쓰는 것: Gemini, Speech-to-Text(chirp_3), 컨텍스트 캐싱, ADK, Cloud Run, Firestore, Cloud Trace(제안), Vertex AI Search(PDF 파싱만, pypdf와 비교 후 결정).
- ADK는 2.11을 쓴다. 2.x는 OpenTelemetry 1.42 이하를 요구해서 FastAPI를 0.141.1로 고정했다 (0.142 이상은 1.44 이상 요구). websockets는 16.1에서 15.0.1로 바뀌었다. 테스트 435개 통과.
- 답변 캐시 저장소 (제안, 사용자 확인 대기): 방송 안은 서버 메모리, 방송 간 재사용은 Firestore. Memorystore는 VPC 설정과 상시 비용이 들고, 한 방송은 한 인스턴스에서 돌아 이점이 없다.
- 캐시 답변이 1초를 못 맞추는 원인은 저장소가 아니라 캐시 조회 전에 도는 댓글 분류(LLM 약 1.3초)다 (`docs/eval/latency.md`). 임베딩으로 같은 질문을 바로 찾아 분류를 건너뛰는 단계를 제안한다.
- 캐시 키 (10/5 사용자 지시: 질문과 제품 정보를 섞어 만든다). 지금도 그렇다. 답변 캐시 키는 제품 ID·질문 유형·조건·정규화한 대표 질문·프로모션 상태·제품 문서 버전이고 (`backend/app/logic/cache.py:15-21`), 분류 캐시 키는 정규화한 댓글·방송 중인 제품이다 (33행). 방송 간 공유 때는 "제품 문서 버전"을 세션 안 숫자에서 **제품 문서 내용 해시**로 바꾼다. 임베딩으로 같은 질문을 찾을 때도 같은 제품 안에서만 찾는다.
- **답변 재사용 범위 (10/5 사용자 결정).** "방송 안"은 라이브 한 편 안에서의 재사용(방송이 끝나면 버림), "방송 간"은 같은 제품의 다른 날 방송에서의 재사용이다. **제품 문서 버전(내용 해시)을 키에 넣는다.**
- 질문 찾기 (제안, 확인 대기): 분류 LLM이 지금처럼 질문 키 목록(`OPEN_GROUPS`)을 보고 고른다. 범위를 이번 방송 최근 30개에서 같은 제품의 지난 방송 질문까지 넓히고, 제품당 상한 50개, 지난 방송 목록은 명시적 캐싱에 넣는다. 임베딩은 쓰지 않는다. 분류 LLM의 다른 일(댓글 종류·제품·유형·조건·대표 질문)을 대신할 수 없어 홉만 늘어난다. 캐시 답변 목표는 "분류 한 번(약 1.3초) 이내"로 바꾼다.
- **저장소 (10/5 사용자 확정):** 방송 안은 서버 메모리(1시간 방송 질문 200개 기준 약 0.4MB), 방송 간은 Firestore.
- 질문 키가 제품당 50개를 넘을 때 (제안): 많이 물어본 순 → 최근 순으로 50개만 프롬프트에 넣고, 이번 방송 질문은 항상 넣는다. 목록에 없는 질문도 분류 결과(유형·조건·대표 질문)로 만든 캐시 키(`answer_cache_key`)가 같으면 답변을 재사용한다. 50은 시작값이다 (키 하나 약 30토큰).
- 답변 재검사 방법 (제안): 인용 문장이 새 문서에 그대로 있는지 `quote_in_passage`(`logic/verify.py:34`)로 보고, 있으면 새 문단으로 연결을 바꿔 `verify_answer`(`logic/verify.py:55`)를 다시 돌린다 (인용 존재, 제품 일치, 답변의 모든 숫자가 인용 안에 있는지, 금지·미승인 표현). 하나라도 실패하면 방송 전에 다시 만든다.
- 제품 정보가 바뀔 때 (제안, 확인 대기). 새 LLM 에이전트는 두지 않는다. 상품 업로드 확정 때 코드로 처리한다.
  1. 파싱 후 문서 내용 해시를 지난 버전과 비교한다. 같으면 끝이다.
  2. 다르면 저장된 답변마다 인용한 문단의 문장이 새 문서에 그대로 있는지(D-048 방식) 보고, `verify_answer`로 숫자·효능 표현을 다시 검사한다.
  3. 통과한 답변은 새 버전으로 옮겨 재사용하고, 실패한 답변은 방송 전에 기존 답변 에이전트로 다시 만든다.
  4. 가격·프로모션 답변(`PRICE_INTENTS`)은 방송 간 재사용하지 않는다.
  5. 운영자 화면에 바뀐 항목(구조화 필드 비교)과 유지·재생성 답변 수를 보여준다.
- BigQuery Graph: 방송 중에는 쓸 수 없다(쿼리 수 초). 방송 후 분석용이라 지금 범위 밖이다. 덱의 로드맵으로 둔다.

## 8. 논의 기록

참여: 사용자(최종 결정), Claude(조율), codex(`gpt-6-astra`), agy(`gemini-3.8-flash-high`). 두 모델은 각각 세션 하나로 기록을 이어 쓴다.

- **10/4 프레임워크 조사.** 두 모델 모두 "3초 경로 앞에 LLM 라우터를 두지 말라"고 결론 냈다. agy의 "ADK 오버헤드 100~300ms"는 실측(1~10ms)으로 반박됐다. agy가 인용한 "Jev 정확도 67.8%"는 TypeSafe 자체 업무 벤치마크에서 다른 모델 답과 일치한 비율이라, 분기 정확도로 볼 수 없다.
- **10/4 팩트 정규식 게이트.** agy는 숫자 정규식으로 팩트 호출을 줄이자고 했다. 평가 문장의 숫자가 철자형("thirty-two dollars")이고 숫자 없는 팩트(질감, 사용법)도 있어서, 운영 경로에는 넣지 않았다.
- **10/5 결선 확률.** Claude 54%, codex 30% (배포 변수 제외). 상위 200팀 단계와 등록자 수를 반영해 약 35%로 맞췄다.
- **10/5 고도화 1~2라운드.** 셋의 안에서 ADK 지휘자, 연속 발화 처리, 처음 보는 문장 평가가 공통이었다. 이미지·영상 검증, 배너 검사, 싱가포르 진행자 섭외, 한국 팩 여부가 쟁점이었다.
- **10/5 사용자 결정.** 목표를 ROI와 초보자 1인 방송 지원으로 다시 세웠다. 방송 밖 기능과 학습 기능은 제외했다. 오케스트레이터는 AI PD로 정의했다.
- **10/5 고도화 3라운드.** 두 모델 모두 AI PD를 사건 기반, 말할 문장 표시, 고정 카드 하나로 설계하자고 했다. codex는 1인 모드의 운영자 의존(민감 질문, 미검증 답변)을 찾아냈다. agy의 "AI가 MD·심의·PD 1명씩 절감" 문구는 측정 근거가 없어 쓰지 않기로 했다.

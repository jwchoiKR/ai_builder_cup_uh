# 확장성·가용성 계획 (10/6)

사용자 목표(10/6): 처음 보는 제품에서 탐지 95% 이상. 서비스 확장성과 가용성 보장. 방송 상태와 질의/응답 캐시를 서버 메모리에만 두지 않는다.

이 계획은 독립 검토자 셋(검토자 A, 검토자 B, 비평 세션)의 검토와 반박 한 라운드를 거쳐 합친 것이다. 원문은 레포 밖 `sealed_sets/results/`에 있다.

## 1. 지금 상태 (코드 확인)

- 방송 하나가 서버 프로세스 하나의 메모리에 통째로 있다. `STORE=memory`이고, `FirestoreStore`는 `NotImplementedError`만 낸다.
- 세션 런타임에는 락, 댓글 분류 캐시, 질의/응답 캐시, 속도 제한, 판정 파이프라인 상태 약 20개, AI PD 상태, 타이머가 들어 있다.
- 화면 전송(SSE)과 이벤트 번호는 프로세스 안에서만 돈다. 인스턴스끼리 주고받는 통로가 없다.
- 배포는 최대 1대, 최소 0대다. 재시작, 배포, 1시간 타임아웃이 나면 진행 중인 방송이 사라진다.
- 영구 저장되는 것은 온보딩 파일·릴리스·팩(GCS, D-263)과 로그뿐이다.

## 2. 세 검토자가 합의한 것

- 먼저 재시작 복구를 증명한다. 여러 대 확장은 그다음이다.
- 방송마다 쓰는 인스턴스는 하나다(owner). 읽는 화면은 어느 인스턴스에서든 받는다.
- owner는 진행자 마이크 연결을 받은 인스턴스가 된다. Firestore 트랜잭션으로 임대를 가져가고 번호(epoch)를 1 올린다. 하트비트 임대는 주 방식으로 쓰지 않는다.
- owner의 모든 쓰기는 epoch를 트랜잭션 안에서 확인한다. 옛 owner의 늦은 쓰기는 거절한다.
- 작업 상태는 owner 메모리에 두고, Firestore는 영구 사본으로 쓴다. 1초 tick이 락을 잡은 채 저장소를 읽지 않게 바꾼다.
- 이벤트는 번호를 문서 id로 하는 "생성만 허용" 쓰기로 바꾼다. 지금은 덮어쓰기라 인스턴스 둘이 쓰면 이벤트가 사라진다.
- 경고 id는 (세션, 문장, 종류, 규칙 또는 칸)으로 정해지는 값으로 바꾼다. 지금은 무작위 id라 장애 뒤 다시 판정하면 경고가 중복된다.
- 진행자 화면 명령(승인, 무시)은 어느 인스턴스에서든 Firestore 트랜잭션으로 처리한다.
- 브라우저는 마이크 음성을 잠시 들고 있다가, 다시 연결되면 마지막으로 확인받은 지점부터 다시 보낸다.
- 화면 전송은 인스턴스·방송마다 Firestore 리스너 하나(또는 300 ms 폴링)로 받아 SSE로 나눠 준다. 시청자마다 리스너를 따로 열지 않는다.
- Redis(Memorystore)와 Pub/Sub은 지금 쓰지 않는다. Firestore 전달 지연이 합격선을 못 넘을 때만 다시 본다.
- 방송 간 공유 질의/응답 캐시는 미룬다. 가격·혜택·문서 버전이 다른 방송에 틀린 답을 줄 위험이 있다. 방송 안 캐시는 owner 메모리와 Firestore 사본으로 충분하다.

## 3. 갈렸던 것과 결론

| 쟁점 | 의견 | 결론 |
|---|---|---|
| 화면 전송 | 검토자 B: 처음부터 Redis. 검토자 A·비평 세션: Firestore로 먼저 하고 실측 | Firestore로 먼저 하고, 실측한 p95로 판단 |
| "생성만 허용"이면 번호표가 저절로 생기나 | 비평 세션: 그렇다. 검토자 A: 아니다. 옛 owner가 안 쓴 번호로 쓰면 성공한다 | epoch를 모든 쓰기에서 트랜잭션으로 확인 |
| 5초마다 상태 저장 | 검토자 B 초안. 검토자 A: 확인받은 입력을 잃는다 | 입력과 결정은 바로 저장, 계산 상태만 메모리 |
| 장애 중 문장 | 비평 세션: 다시 판정하거나 "놓침"으로 표시. 검토자 A: 표시만으로는 손실 0이 아니다 | 음성 버퍼 재전송으로 다시 판정, 표시는 최후 수단 |

## 4. 순서 (단계마다 배포하고 잴 수 있게)

1. 시험 도구와 합격선 고정. 지금 지연과 손실 지점을 계측한다.
2. 한 인스턴스에서 영구 저장: FirestoreStore, 정해진 경고 id, 생성만 허용하는 이벤트, tick 수정. 시험: 방송 중 재배포 후 복구.
3. 음성 버퍼와 재전송, 저장된 마감 시각으로 타이머 다시 걸기, SSE 이어받기.
4. 두 번째 인스턴스: epoch 확인, 마이크 넘겨받기, 어느 인스턴스에서든 명령 처리, 인스턴스별 리스너.
5. 방송 K개 부하 시험. 처음 막히는 곳을 잰다(Vertex·STT 할당량일 가능성이 크다).

## 5. 합격선 (시험 전 고정)

- 복구: 따뜻한 인스턴스 2대에서 방송 중 owner 강제 종료 10회와 재배포 1회. 종료부터, 장애 뒤 말한 문장의 경고가 화면에 뜰 때까지 매회 10초 이하.
- 손실과 중복: 확인받은 입력·명령 손실 0, 화면에 보이는 경고 중복 0, 덮어쓴 이벤트 0, 옛 epoch 쓰기 성공 0, 소리 없이 사라진 음성 0.
- 분리 시험: owner를 25초 멈췄다 살렸을 때 옛 owner의 쓰기 성공 0.
- 지연: 방송 1개와 10개(방송마다 마이크 1, 시청자 20, 댓글 분당 30, 1분간 5배 폭주), 설정마다 경고 문장 1,000개 이상. 말 끝부터 화면 표시까지 p95 3초 이하. owner가 아닌 인스턴스의 저장 후 화면 표시 p95 300 ms 이하.
- 비용: 쉬는 방송 1개당 Firestore 읽기 초당 3회 이하. 방송 1시간당 비용을 보고한다.

## 6. 사용자 결정이 필요한 것

- 방송이 있는 동안 최소 인스턴스 2대 유지(비용 발생). 1대면 대체 인스턴스가 처음부터 떠야 해서 복구 25초 안팎이 된다(추정, 미측정).
- Firestore 사용: 데이터베이스 `live-studio`는 이미 있다. Cloud Run 서비스 계정에 Firestore 권한(IAM)이 필요하다.
- 개발 순서: 개발 세션 하나가 정확도 작업과 이 작업을 나눠야 한다.

## 7. 심사위원 시점

- "재시작하면 방송이 사라진다"는 확장성 이전의 가용성 문제다. 2단계(한 인스턴스 영구 저장과 재배포 복구)만 끝나도 지적 하나가 사라진다.
- "여러 대로 확장한다"는 주장은 4~5단계 시험 숫자가 있어야 믿는다. 숫자 없이 구조도만 보여 주면 감점이다.
